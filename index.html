Metrics explained

Every number ComputeFit shows: what it means, how it is calculated, and what a good value looks like. The ? next to a result opens its entry here.

Verdict & options

These apply to every model type.

Verdict

Meets your targets: every check passes with at least 15% to spare. Meets targets, no margin: everything passes, but at least one check is within 15% of its limit, so a small change in the real pipeline can tip it over. Does not meet targets: at least one check fails.

Aim for "meets your targets". "No margin" is fine for a demo, risky for production.

Headroom ×

How much spare capacity a setup has: the tightest of all its checks.

headroom = min( capacity ÷ demand, limit ÷ delay, 0.9 × free memory ÷ memory needed )

1.0× means exactly at the limit; 2.0× means it could handle twice the load.

≥ 1.5× is the bar for "Recommended": room for more cameras/users and traffic peaks.

Bottleneck — "what's holding it back"

The single resource that limits the result. One of: memory (the model doesn't fit), compute (not enough TFLOPS — typical for vision and image generation), memory bandwidth (typical for LLM text generation), or CPU pre/post-processing (resizing frames and decoding results on a slow CPU).

Fix the bottleneck first — upgrading anything else won't help.

Free fix

ComputeFit tries cheaper settings on your current hardware, in order of least quality impact (optimized runtime → lower precision → smaller input or fewer image tokens → smaller model), and shows the first one that passes every target, with its trade-off.

Budget · Recommended · Performance

Budget: cheapest setup that passes every target. Recommended: cheapest setup with ≥ 1.5× headroom (if the cheapest already has that, it's labeled "Recommended · best value"). Performance: most headroom within ~2–4× the price of the recommended option.

If you already own an edge device, options stay on edge devices. Budget, power limit and "edge only" filters apply to all three.

Computer vision

Detection, segmentation, oriented boxes (OBB), pose, classification, promptable segmentation (SAM) and depth.

Delay per frame ms

Time from a camera frame arriving to its detections being ready.

delay = runtime overhead + model compute + pre/post-processing model compute = (GFLOPs × batch + fixed work) ÷ effective TFLOPS

Video decoding and network transport are not included.

Real-time control (robots, drones): ≤ 40 ms. Inspection lines: ≤ 20 ms. Monitoring / CCTV: 100–300 ms is fine.

Frames per second (FPS)

Maximum frames the setup can process per second across all cameras, compared with what you need: cameras × FPS each.

FPS = devices × min( batch × 1000 ÷ inference ms, CPU pre/post capacity )

Cameras @ N FPS in the options is simply FPS ÷ N, rounded down.

Memory GB

Memory the model needs versus what the device can actually use.

vision: weights + activations (∝ GFLOPs × batch) + runtime context image gen: image model + text encoder + VAE + activations + runtime LLM: weights + KV cache + runtime VLM: language model + vision encoder + KV cache + runtime

Usable memory: 92% of a GPU, 65% of a Jetson (shared with the OS), 70% of Apple unified memory, 60% of system RAM.

GFLOPs

Billions of math operations for one image — the model's "size of work". Published by model authors at a reference input size (640 px for YOLO detection, 1024 px for OBB and SAM, 224 px for classification).

GFLOPs at your size = published GFLOPs × (your size ÷ reference size)²

Input size px

The square resolution frames are resized to before the model. Halving it cuts compute ~4×, but small or distant objects get harder to detect.

Use the size the model was trained at (your catalog models: 640) unless speed forces a change — then retrain at the new size.

Precision — FP32 · FP16 · INT8

Number format for weights and math. FP16 is ~2× faster than FP32 on GPUs and Jetson with no practical accuracy loss. INT8 is another ~1.7× faster but needs calibration images and usually costs 0.5–2 mAP. Hailo accelerators run INT8 only.

Default to FP16; use INT8 when you need the speed and have validated mAP.

Runtime

The software that executes the model. "Best for the device" means TensorRT (NVIDIA GPUs and Jetson), OpenVINO (Intel), NCNN (Raspberry Pi CPU), HailoRT (Hailo), Core ML (Apple). ONNX Runtime is assumed ~30% slower; plain PyTorch ~2× slower plus Python overhead.

Batch

Frames from several cameras processed together. Raises total FPS because the accelerator is used more efficiently, but adds a little delay. Assumed up to 8 on GPUs, 4 on Jetson, 1 on CPUs and Hailo.

Pre/post-processing

Work around the model on the CPU: resizing and normalizing the frame, then decoding boxes and running NMS (non-maximum suppression, which removes duplicate boxes). YOLO26 and RT-DETR are NMS-free, so this step is ~40% lighter; segmentation masks make it ~40% heavier.

Image generation

Diffusion models (Stable Diffusion, SDXL, SD 3.5, FLUX) build an image over many denoising steps, so they are compute-bound and measured in seconds.

Time per image s

Seconds until a finished image, including waiting in the queue at your peak rate. "When idle" is the time with no other requests.

idle time = steps × time per step + VAE decode + text encoding time at peak = idle × (1 + ρ ÷ (2 × (1 − ρ))) ρ = demand ÷ capacity

Interactive tools: ≤ 5–10 s. Batch jobs: anything that meets images/hour.

Images per hour

Maximum sustained output. Each GPU runs its own model copy, so more GPUs add throughput, not single-image speed.

images/hour = GPUs × 3600 ÷ idle time × images per request

Keep demand below ~70% of capacity, or waiting time grows quickly.

Steps · steps/s

Number of denoising passes (25–30 typical, 4 for distilled "Lightning / Turbo / schnell" models). Steps/s is how many passes the GPU does per second at your resolution.

time per step = GFLOPs per step × (pixels ÷ native pixels)^1.2 ÷ effective TFLOPS

Text encoder · offloading

The model that turns your prompt into numbers (CLIP, or the large T5-XXL in SD 3.5 and FLUX at ~9.5 GB in FP16). It runs once per prompt, so moving it off the GPU after encoding saves a lot of memory for ~1–3 s extra.

FP16 · FP8 · NF4

FP8 halves memory and is ~1.4× faster on GPUs with FP8 tensor cores (RTX 40/50, L4, L40S, H100+); elsewhere it only saves memory. NF4 / GGUF Q4 cuts memory ~3.5× for a slight loss of fine detail and is ~15% slower.

LLM

Text models generate one token (≈ ¾ of a word) at a time.

Speed per user tokens/s

How fast the answer appears for each user. Each token reads all active weights from memory, so speed is usually limited by memory bandwidth.

time per token = max( bytes read ÷ effective bandwidth, FLOPs ÷ effective compute ) + overhead

Reading speed is 5–8 tokens/s; chat feels fast at 20+; coding agents want 50+.

Time to first word ms

Delay before the answer starts: the model must read the whole prompt first. This is compute-bound; with several users it assumes a quarter of them send a prompt at the same moment.

≈ 2 × active parameters × prompt tokens ÷ (TFLOPS × 45%)

KV cache · context

Memory that stores the conversation so far, for every user. It grows with context length × users and often matters as much as the weights.

KV bytes = 2 × layers × KV heads × head dim × context × users × bytes per value
VLM (vision-language models)

A VLM turns each image into tokens, reads them like a long prompt, then writes an answer. Use it for open questions, reading text and describing scenes; for a fixed list of objects a detector is far cheaper.

Time per answer s

Seconds from sending the image and question to the complete answer.

time = vision encoder + reading image and text tokens + answer tokens ÷ tokens per second

Reading the image is compute-bound; writing the answer is limited by memory bandwidth.

Interactive use: ≤ 3–5 s. Camera event checks: ≤ 2 s. Documents and batch jobs: 10–30 s is fine.

Answers per minute

Maximum sustained requests. On GPUs several requests run in parallel (up to 32) while memory allows; other devices up to 4.

answers/min = parallel requests × 60 ÷ time per answer

Image tokens

How many tokens one image becomes. Some models use a fixed count (Gemma 3: 256, Moondream: 729); others scale with resolution.

tokens = (resolution ÷ pixels per token)² e.g. Qwen2.5-VL: 28 px per token → 768 px ≈ 750 tokens

Halving the resolution cuts image cost about 4×. Crop to the region of interest first.

Accuracy trade-offs

Lower precision makes a model smaller and faster, but can cost accuracy. Each result shows a small table: speed, memory and the typical quality change for every precision, and whether that option meets your targets.

Quality change

FP16 / BF16 is treated as lossless. FP8 and 8-bit are usually close to lossless. 4-bit language models lose a little (about 1% perplexity on a 7B model, more on small ones). Detectors lose about 1–7 mAP points in INT8 with simple post-training quantization; quantization-aware training recovers most of it. Robot policies are mostly unaffected, but precise tasks can degrade at 4-bit.

Rule of thumb: start at FP16, move to FP8 / INT8 when you need speed or memory, and only go lower after testing on your own data.

Stack planner

Several models on one device compete for memory and compute. The planner adds up the memory (each model's weights and buffers, with the shared runtime counted once) and the load: every model's share of the device's capacity when it runs alone, summed. A combined load under 100% means the stack keeps up; under about 85% leaves room for peaks. With several GPUs, models are spread across them.

combined load = Σ (1 ÷ headroom of each model alone) · stack headroom = 1 ÷ combined load

Sharing a device also adds waiting time between models, so a model with a tight latency target may need its own GPU.

VLA (robot-control models)

A vision-language-action model looks at camera images plus an instruction and outputs robot actions. Robots need a steady stream of actions, so what matters is how quickly a new camera frame turns into motion, and how many actions per second the model can supply.

Reaction time ms

Time from a camera frame arriving to the first new action being ready. It is the delay in the control loop: the robot is always acting on slightly old information.

reaction = vision encoder + reading cameras and instruction + action generation + software overhead

Action generation is either autoregressive (one token per action dimension, e.g. OpenVLA) or a few flow / diffusion steps over a whole chunk (π0, SmolVLA, GR00T).

Slow tabletop tasks: ≤ 200–300 ms. Dynamic manipulation: ≤ 100 ms. Whole-body humanoid control: ≤ 40 ms (usually with a faster low-level controller underneath).

Actions per second Hz

Many VLAs predict a chunk of future actions per inference. Running them back to back, the model can supply this many actions per second. It is an upper bound for open-loop execution; how fast the robot reacts to new images is still set by the reaction time.

actions per second = actions per chunk ÷ time per inference

Common control rates: 10 Hz (arms, teleoperation datasets), 30–50 Hz (dexterous), 50–100 Hz (humanoid joints).

Chunk and denoising steps

Chunking predicts, say, 50 actions at once so the robot can keep moving while the next inference runs (asynchronous inference, real-time chunking). Flow / diffusion action heads repeat a small network several times; fewer steps are faster.

Halving the denoising steps usually saves 10–40% of the time with little quality loss.

VLA numbers are calibrated to published latencies (π0 about 73 ms on an RTX 4090, OpenVLA about 6 Hz on an RTX 4090, GR00T N1 about 64 ms on an L40) and are estimates; optimised engines can be 1.5–2× faster, newer models are best added through data.json.

Hardware specs

Values come from the data tables at the top of the page source and can be edited there.

TFLOPS · effective TFLOPS

TFLOPS is the vendor's peak dense tensor throughput (FP16 or FP8). Real models never reach it. Effective TFLOPS is what a model actually gets: for vision CNNs about 30% of peak on GPUs, calibrated so that the T4 matches Ultralytics' published YOLO26 latencies. Small models get less, because fixed per-inference work dominates.

Memory bandwidth GB/s

How fast data moves from memory to the chip. It decides LLM generation speed. Datacenter HBM GPUs reach 2–8 TB/s versus ~0.3–1.8 TB/s for consumer cards; Jetson boards are 25–205 GB/s.

Power W

Typical board power (TDP) — used for the max-power filter and electricity cost. Edge devices: 10–60 W; desktop GPUs: 165–575 W; datacenter GPUs: 70–1000 W.

Costs

Price · cloud price

Approximate USD street price per device, or approximate cloud rental per GPU-hour. Prices change often — check current listings.

Rent vs buy

rent per month = $/hour × GPUs × hours per day × 30 buy = price × GPUs × 1.25 (host machine) power per month = W × GPUs × 70% load × hours × 30 ÷ 1000 × $/kWh pays off after = buy ÷ (rent − power) months

Steady daily use favors buying; occasional or bursty use favors renting.

Accuracy & sources

ComputeFit is a roofline-style estimate: it combines published model sizes with device specs, then calibrates against published benchmarks. Expect real results within roughly ±20–30%. Drivers, runtime versions, camera decoding and your exact pipeline all move the numbers.

What's calibrated

YOLO26 detection latencies on a T4 with TensorRT (the model lands within ~0.3 ms of the published 1.7–11.8 ms), RT-DETR-l on T4, SAM 2.1 on A100, typical SDXL and FLUX speeds on RTX 4090 and H100, and LLM speeds from memory bandwidth.

What's approximate

FLOPs for YOLO26 seg/pose/OBB/cls variants (derived from the YOLO11 equivalents), edge-device speeds (estimated from typical public benchmarks), all VLM results (image-token counts depend on each model's tiling and the image's aspect ratio), and all prices. Validate on the real device before buying.
